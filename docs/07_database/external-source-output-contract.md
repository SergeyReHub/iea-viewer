---

## О документе

Этот файл — **полная спецификация** того, как должна быть устроена PostgreSQL-база на выходе трансформации, чтобы её без доработок схемы подключил **read-only веб-viewer** (отчёты, фильтры, справочники, журнал загрузок).

**Ваша зона ответственности:** загрузка, валидация, DDL, наполнение данными, документация схемы, read-only доступ.

**Зона ответственности заказчика (после приёмки БД):** подключение строки `postgresql://…`, регистрация источника в viewer. Детали реализации viewer вам не требуются.

**Эталон реализации:** действующая БД источника IEA (`iea_data`) — структура ниже воспроизводит проверенный на практике контракт.

---

## 1. Контекст потребителя

Viewer — веб-приложение (Vue + FastAPI), которое:

- подключается к PostgreSQL **только на чтение**;
- **не** загружает файлы и **не** меняет DDL;
- показывает справочники, таблицы фактов, сводные отчёты (pivot), тепловые карты покрытия данных;
- строит фильтры-деревья по справочникам с иерархией;
- отображает журнал ETL-прогонов и ошибки валидации.

Все бизнес-правила агрегации, топ-N, доли в структуре и т.п. должны быть **уже заложены в fact-слой** или однозначно выводиться из нормализованных измерений.

---

## 2. Общая схема

```
[Сырые данные источника]
        ↓
[Ваш ETL / staging]        ← viewer не читает
        ↓
[Выходной слой PostgreSQL] ← viewer читает только этот слой
        ↓
[Веб-viewer, read-only]
```

Подключение на стороне заказчика (для справки):

- одна БД = один логический источник;
- строка подключения вида `{SOURCE_ID}_DB_URL=postgresql://user:pass@host:5432/dbname`;
- идентификатор источника — латиница, нижний регистр (`eurostat`, `jodi`, `eia`).

## 3. Структура схем PostgreSQL

### 3.1. Схемы

| Схема | Назначение | Обязательность |
|-------|------------|----------------|
| `base` | Общие справочники, журнал загрузок, ошибки | **Обязательно** |
| `{domain}` | Предметные данные (`oil`, `gas`, `trade`, `energy` …) | Одна или несколько |
| `staging`, `raw`, … | Промежуточные слои | По желанию; viewer **не читает** |

### 3.2. Именование таблиц

| Префикс | Тип | Назначение |
|---------|-----|------------|
| `ref_*` | Справочник | Коды, названия, иерархии |
| `fact_*` | Факт | Числовые показатели |
| `map_*` | Маппинг | Старые / внешние коды → канонические |

Полное имя: **`{schema}.{table}`**, например `trade.fact_trade_flow`.

Viewer обращается к таблицам по полным именам. Имена должны быть **стабильны между релизами**; смена кода — через `map_*`, не переименование колонки.

## 4. Обязательный слой `base`

### 4.1. `base.ref_data_source`

Реестр логических источников внутри одной БД (если их несколько).

| Колонка | Тип | Комментарий |
|---------|-----|-------------|
| `source_id` | PK | Стабильный ID |
| `domain` | text | Доменная схема |
| `source_code` | text | Код для UI |
| `source_name` | text | Отображаемое имя |
| `is_primary` | boolean | Ровно один `true` — дефолт для фильтрации |

### 4.2. `base.load_batch`

Журнал прогонов ETL (отображается в админке viewer).

| Колонка | Тип | Комментарий |
|---------|-----|-------------|
| `batch_id` | PK | UUID или bigint |
| `source_id` | FK | → `ref_data_source` |
| `domain` | text | |
| `file_name` | text | nullable |
| `file_hash` | text | nullable |
| `status` | text | `RUNNING`, `COMPLETED`, `FAILED` |
| `records_read` | int | |
| `records_inserted` | int | |
| `records_updated` | int | |
| `records_skipped` | int | |
| `records_error` | int | |
| `started_at` | timestamptz | |
| `completed_at` | timestamptz | nullable |
| `error_message` | text | nullable |
| `created_by` | text | nullable |

### 4.3. `base.validation_error`

| Колонка | Тип |
|---------|-----|
| `error_id` | PK |
| `batch_id` | FK |
| `error_type` | text |
| `error_severity` | text |
| `record_data` | jsonb |
| `error_message` | text |
| `table_name` | text |
| `created_at` | timestamptz |

### 4.4. `base.ref_country`

**Обязательно**, если в фактах есть географические измерения. Viewer строит деревья фильтров рекурсией по `parent_code`.

| Колонка | Тип | Комментарий |
|---------|-----|-------------|
| `country_code` | PK, text | Стабильный код: `GERMANY`, `OECDTOT`, `EU27_2020` |
| `country_name` | text | Название (EN) |
| `country_name_ru` | text | Название (RU), желательно |
| `parent_code` | text, nullable | `NULL` только у корней дерева |
| `iso2`, `iso3` | text | Опционально |

**Правила иерархии:**

- **листья** — отдельные страны (нет дочерних узлов с этим кодом как parent);
- **узлы** — региональные агрегаты (`OECDTOT`, `WORLD`, `NON_OECDTOT`);
- коды **не переименовываются** между версиями; устаревшие — через `map_*`.

Если ваша география хранится в другой таблице — в поставке явно укажите маппинг: «колонка X в fact = `country_code` из `geo.ref_territory`» и приведите эквивалентную иерархию.

### 4.5. Дополнительные справочники `base` (по необходимости)

| Таблица | Когда нужна |
|---------|-------------|
| `base.ref_unit` | Разные единицы: `KT`, `TJ`, `KWH`, `BBL` |
| `base.ref_frequency` | Частоты: `A`, `Q`, `M`, `W`, `D` |
| `base.ref_energy_flow` | Потоки баланса: `IMPORTS`, `EXPORTS`, `STOCKCHG` |

Структура каждого `ref_*`: `{entity}_code`, `{entity}_name`, `{entity}_name_ru`, `parent_code` (для иерархий).

## 5. Факт-таблицы `fact_*`

### 5.1. Обязательные колонки

| Колонка | Тип | Комментарий |
|---------|-----|-------------|
| `value` | numeric | `NULL` = нет данных; **не путать с нулём** |
| `time_period` | text | Формат — см. §6 |
| `frequency_code` | text | `A` / `Q` / `M` / … |
| `unit_code` | text | Единица из `ref_unit` |
| `source_id` | FK | → `ref_data_source` |
| `load_batch_id` | FK | → `load_batch` |

### 5.2. Рекомендуемые колонки

| Колонка | Тип | Комментарий |
|---------|-----|-------------|
| `id` | bigserial | Технический PK |
| `qualifier` | text | Качество значения |
| `conf_status` | text | Конфиденциальность |
| `time_period_start` | date | Начало интервала (для M/D) |
| `old_data` | jsonb | Сырой фрагмент источника (отладка) |
| `created_at`, `updated_at` | timestamptz | Аудит строки |

### 5.3. Стандартные измерения (имена колонок — контракт)

Viewer автоматически распознаёт фильтр, **если колонка с таким именем есть** в таблице:

| Колонка | Назначение |
|---------|------------|
| `country_code` | Страна (баланс, производство) |
| `reporter_code` | Страна-репортер (торговля) |
| `partner_code` | Страна-партнёр (торговля) |
| `flow_code` | Поток (импорт/экспорт/запасы) |
| `product_code` | Продукт / товарная номенклатура |
| `indicator_code` | Показатель (электроэнергетика и др.) |
| `plant_type_code` | Тип установки |
| `field_code` | Месторождение |
| `unit_code` | Единица |
| `frequency_code` | Частота |
| `source_id` | Источник данных |
| `qualifier` | Квалификатор |
| `conf_status` | Статус конфиденциальности |

**Не используйте синонимы** (`reporter`, `partner_country`) — viewer их не увидит без отдельной доработки на стороне заказчика.

Доменные справочники продуктов: `{domain}.ref_{domain}_product` с полями `product_code`, `product_name`, `product_name_ru`, `parent_code`.

### 5.4. Семантика `value`

| Ситуация | Хранение |
|----------|----------|
| Данных нет | `value IS NULL` или строка отсутствует |
| Ноль | `value = 0` |
| Региональный итог | Отдельный код в `ref_country` (`TOTAL`, `OECDTOT`), не вычисление в UI |
| Grain | Уникальный индекс на комбинацию измерений + `time_period` + `unit_code` + `source_id` |

### 5.5. Пример: торговая таблица (эталон IEA)

Таблица `oil.fact_oil_trade` — одна строка = объём торговли репортёр → партнёр по продукту, потоку, периоду и единице.

Колонки измерений:

```
reporter_code, partner_code, product_code, flow_code,
frequency_code, time_period, unit_code, value,
qualifier, conf_status, source_id, load_batch_id
```

Типичный запрос, который должен работать:

```sql
SELECT partner_code, time_period, SUM(value::numeric) AS volume
FROM oil.fact_oil_trade
WHERE reporter_code = 'GERMANY'
  AND flow_code = 'IMPORTS'
  AND product_code = 'CRUDE_OIL'
  AND unit_code = 'KT'
  AND frequency_code = 'A'
  AND time_period = '2024'
GROUP BY partner_code, time_period
ORDER BY volume DESC;
```

## 6. Форматы `time_period`

Период хранится как **text**. Внутри одного `frequency_code` — один формат:

| `frequency_code` | Формат | Пример |
|------------------|--------|--------|
| `A` | `YYYY` | `2024` |
| `Q` | `YYYY-Qn` | `2024-Q1` |
| `M` | `YYYY-MM` | `2024-03` |
| `D` | `YYYY-MM-DD` | `2024-03-15` |

Не смешивайте форматы в одной частоте. Актуальность monthly-данных определяется как `MAX(time_period)` при `frequency_code = 'M'`.

---

## 7. Таблицы маппинга `map_*`

Для смены кодов между версиях ETL:

| Колонка | Комментарий |
|---------|-------------|
| `old_code` | Код из источника / предыдущей версии |
| `new_code` | Канонический код в `ref_*` |
| `comment` | Пояснение |

Пример: `CRUDEOIL` → `CRUDE_OIL` в `map_oil_product_old_code`.

---

## 8. Поведение viewer при чтении БД

Это ограничения на ваш дизайн — viewer **не пересчитывает** бизнес-логику:

1. Список колонок — из `information_schema`; фильтры по стандартным именам из §5.3.
2. Деревья фильтров — `WITH RECURSIVE` от строк с `parent_code IS NULL` в `ref_*`.
3. Сводные отчёты — `SELECT` + `GROUP BY` измерений + `SUM(value)`.
4. Heatmap покрытия — `COUNT(*)` по стране × периоду.
5. Трансформации при чтении **не выполняются**.

## 9. Каталог таблиц (что передать вместе с DDL)

Помимо SQL-миграций, передайте машиночитаемый каталог в YAML или JSON:

```yaml
schema_version: "2026-06"
source_id: eurostat
domains:
  - id: trade
    tables:
      - name: trade.fact_trade_flow
        type: fact
        description: "Международная торговля по товарным кодам"
        grain: "reporter × partner × product × flow × period × unit"
        dimensions:
          - reporter_code
          - partner_code
          - product_code
          - flow_code
          - frequency_code
          - time_period
          - unit_code
        measures:
          - value
      - name: trade.ref_product
        type: ref
        description: "Товарная номенклатура"
```

Для каждой `fact_*` обязательно опишите **grain** (что означает одна строка).

## 10. Чеклист приёмки (Definition of Done)

### База и DDL

- [ ] PostgreSQL 14+ (или согласованная версия)
- [ ] Схема `base`: `ref_data_source`, `load_batch`, `validation_error`
- [ ] Справочник географии с `parent_code` (или документированный эквивалент)
- [ ] Все `fact_*` содержат поля из §5.1
- [ ] Уникальные индексы на grain
- [ ] `ref_data_source.is_primary = true` ровно у одной записи

### Данные

- [ ] Минимум 2 территории, 2 периода, 2 значения номенклатуры/потока
- [ ] Есть строки с `value IS NULL` и с `value = 0`
- [ ] Есть завершённый `load_batch` со статусом `COMPLETED`
- [ ] Агрегаты (`TOTAL`, регионы) — отдельные коды в справочнике

### Документация

- [ ] ER-диаграмма или описание схем
- [ ] Data dictionary по каждой `fact_*`
- [ ] Расшифровка кодов агрегатов
- [ ] Каталог таблиц (§9)
- [ ] 5–10 примеров SQL «как в отчёте»

### Доступ

- [ ] Учётная запись PostgreSQL **только SELECT**
- [ ] Тестовая строка подключения для заказчика
- [ ] `SELECT COUNT(*) FROM base.load_batch` выполняется

## 11. Что согласовать с заказчиком до финализации DDL

1. Идентификатор источника (`source_id`) и имя БД.
2. Список доменных схем.
3. Grain каждой `fact_*`.
4. Соответствие колонок §5.3 или явные отклонения.
5. Одна пилотная `fact_*` для первого отчёта в viewer.

После приёмки БД заказчик подключает источник в viewer; доработка схемы с вашей стороны не потребуется, если контракт соблюдён.

## 12. Антипаттерны

| Нельзя | Почему |
|--------|--------|
| Один JSONB вместо нормализованных `fact_*` | Нет фильтров и pivot |
| Только numeric ISO без text-кодов | Нет подписей и пресетов |
| Разные единицы в `value` без `unit_code` | Некорректные суммы |
| Иерархия через `level` без `parent_code` | Не строятся деревья фильтров |
| Переименование колонок между релизами | Ломаются отчёты |
| Агрегаты только в UI | Расхождение с топ-N и долями |
| Нестабильные имена колонок во VIEW | Viewer читает `information_schema` базовой таблицы |

## 13. Приложение: ориентир по доменам IEA (эталон)

Для понимания масштаба — действующий эталон `iea_data`:

| Схема | Содержание |
|-------|------------|
| `base` | `ref_country`, `ref_unit`, `ref_frequency`, `ref_energy_flow`, `ref_data_source`, `load_batch`, `validation_error`, `map_*_old_code` |
| `oil` | 8× `fact_*`, `ref_oil_product`, `ref_oil_field`, `map_oil_product_old_code` |
| `gas` | 2× `fact_*`, `ref_gas_product` |
| `coal` | 4× `fact_*`, `ref_coal_product` |
| `electricity` | 5× `fact_*`, `ref_electricity_*` |

Ваш источник может иметь другой набор доменов; важно соблюдение **контракта имён и типов**, а не копирование всех таблиц IEA.
